## 1. สิ่งที่ต้องนำไปคุยให้เห็นภาพ

เสนอ **10 หน้าจอหลัก + 3 แบบฟอร์มป๊อปอัป** โดยรวมขั้นตอนเป็นแท็บในหน้าเดียว รวมจาก 21 มุมมองของ Atlas ฉบับเก่า เป้าหมายการพัฒนาเรียงจาก **เข้าใช้ → เห็นทะเบียนเอกสาร → เปิดไฟล์ → นำเข้าไฟล์จริง → สร้างเอกสารและรหัส → เดินงาน A/B ตามสิทธิ์**

SRS มี Use Case 28 ตัว ไม่ได้แปลว่าต้องมี 28 หน้า แบบรอบนี้มี 23 ตัวในเส้นทางสาธิตหลัก และรวม UC-A-11 ในหน้า DAR เป็น **24 ตัวในแบบ พักเต็ม 4 ตัว** แต่ **ไม่อ้างว่าครบทุก FR/AC** โดยเฉพาะประเภท DAR และข้อยกเว้นทั้งหมด

### ตีความคำสั่งอาจารย์เป็นงานที่ตรวจรับได้

| คำสั่ง | งานที่เสนอ | เกณฑ์สาธิต |
|---|---|---|
| Hardcode user ไม่สมัคร | สร้างบัญชีตัวอย่างคงที่ เลือกบทบาทแล้วสลับเป็นผู้ใช้ตัวอย่างของบทบาทนั้น พร้อมอีเมล/รหัสผ่าน | ชื่อ บุคคล บทบาท เมนู และข้อมูลที่มองเห็นเปลี่ยนสอดคล้องกัน ไม่ใช่เปลี่ยนเฉพาะป้ายชื่อ |
| หาวิธีนำไฟล์เข้า | แบบเลือกไฟล์ PDF และข้อมูลกำกับ เก็บไฟล์จริงพร้อมรายการในฐานข้อมูล | อัปโหลดแล้วค้นเจอ เปิดไฟล์ได้ รีโหลดแล้วยังอยู่ และผู้ไม่มีสิทธิ์เปิดไม่ได้ |
| Document code เจนเอง | สร้างรหัสเอกสารใหม่ตาม QP-2301-0107 §6.3 และตรวจเลขซ้ำ | ตัวอย่างรหัสถูกโครงสร้าง กดซ้ำ/สร้างพร้อมกันไม่เกิดรหัสซ้ำ; เอกสารเก่านำเข้าด้วยรหัสเดิม |
| โชว์เอกสารทั้งหมดพร้อมข้อมูล | หน้าทะเบียนเป็นจุดเริ่มเดโมของ DCC พร้อมค้นหา กรอง และรายละเอียด | DCC เห็นชุดข้อมูลนำเข้าครบ ผู้ใช้อื่นเห็นตามสิทธิ์ ไม่ใช้คำว่า “ทั้งหมด” เพื่อเปิดข้อมูลทุกอย่างให้ทุกบทบาท |
| Role ทำอะไร/เห็นอะไร | ใช้เมนู × การกระทำ × ขอบเขตข้อมูล และเงื่อนไขสถานะ | เปลี่ยนคนแล้วทั้งเมนูและคำสั่งเปลี่ยน ส่งคำสั่งข้ามสิทธิ์ถูกปฏิเสธ ไม่พึ่งซ่อนปุ่มอย่างเดียว |

**เกณฑ์ปิด DAR ในเดโม:** แสดงรายการตรวจตามประเภทคำขอ อ้างผลอนุมัติและหลักฐานการดำเนินการจริง รวมงานประกาศใช้ แจกจ่าย และเรียกคืนที่เกี่ยวข้อง ผู้มีอำนาจยืนยันปิดได้เมื่อรายการบังคับครบเท่านั้น ระบบบันทึกผู้ปิด วันที่ และประวัติ หากยังขาดงาน/หลักฐานหรือผู้ใช้ไม่มีอำนาจต้องปฏิเสธ การอนุมัติและการรับทราบไม่ใช่หลักฐานว่าปิด DAR ได้โดยอัตโนมัติ ไม่สร้างหลักฐานสมมติหรือเปิดให้ข้ามข้อบังคับ

### ขอบเขตตัวอย่าง A ที่ควรเริ่ม

นำเข้า **ฉบับประกาศใช้เดิม** ได้ทุกประเภท QM/QP/WI/SD/FM ด้วยรหัสเดิม โดย DCC ไม่สร้าง DAR สมมติเพียงเพื่อนำไฟล์เข้า ส่วนสร้าง/แก้เนื้อหาใหม่ผ่าน DAR:

- **QM:** DCC จัดทำ → ตรวจรับ → QMR ทบทวน → คณบดีอนุมัติ → DCC ประกาศใช้
- **QP/WI:** เจ้าของเอกสารยื่น → ตรวจรับ → รองคณบดีทบทวน → QMR อนุมัติ → DCC ประกาศใช้; WI ต้องเลือก QP ต้นทาง
- **SD/FM ในระบบจริง Step 3:** เจ้าของเอกสารจัดทำ → ผู้คุมทะเบียนตรวจรับ → รองคณบดีทบทวน → QMR อนุมัติ → DCC ประกาศใช้ ตามมติใช้ตาราง §6.2 สำหรับระบบทดลอง (ข้อความ §4 มีอำนาจ FM ต่างกัน เก็บไว้เป็นประเด็นยืนยันทางการ)
- หลังประกาศใช้ ใช้ไฟล์แนบคำขอเดิมต่อในทะเบียน แล้วผู้คุมทะเบียนตรวจงานแจกจ่าย/เรียกคืน แนบหลักฐานและปิด DAR

ผู้ช่วย QMR ทำแทนได้เฉพาะรายการที่ได้รับมอบหมาย และบันทึกชื่อผู้ช่วยเอง ผู้ทบทวนและผู้อนุมัติต้องต่างบุคคล DAR ถือครอง/อื่น ๆ ยังไม่ใช่เส้นทางที่ทำครบใน mockup

UC-A-07 ยกเลิกใช้งานพักจากรอบนี้โดยคง 23 UC เป้าหมายรวมการปิด DAR การอ่านประวัติเอกสารที่ยกเลิกมาแล้วทำได้ตามสิทธิ์ แต่ไม่เพิ่มคำสั่งยกเลิกใหม่ก่อนเส้นทางหลักผ่าน

### Dashboard 6 หมวดและสิทธิ์

1. เอกสาร: จำนวนทะเบียน ประเภท สถานะ และฉบับก่อนหน้า ไม่รวมร่างใน DAR เป็นฉบับประกาศใช้
2. DAR: ทุกขั้นรวมส่งกลับ ยังไม่ปิด และปิดแล้ว; กดลงรายการพร้อมกรองสถานะ
3. รับทราบ: จำนวนมอบหมาย ยืนยันแล้ว และค้าง; ผู้ปฏิบัติงานเห็นเฉพาะบัญชีตน
4. บันทึก/หลักฐาน: จำนวนบันทึก บันทึกที่มีไฟล์ และไฟล์แนบไม่ซ้ำใน Record/Finding/CAR ไม่รวมไฟล์เอกสารควบคุม
5. รอบตรวจ/Finding: รอบ ประเด็น ประเด็นมีใบเปิดค้าง และประเด็นที่ยังไม่มีใบคำร้อง
6. CAR/NCR: จำนวนตาม 8 สถานะ งานเปิด เกินกำหนด และปิดแล้ว; กดลงรายการพร้อมกรองสถานะ

เมนูภาพรวมมีใน DCC, QMR, ผู้ช่วย QMR, Auditor, Lead Auditor และ Sponsor การมีเมนูไม่ได้ทำให้เห็นทุกหมวดโดยอัตโนมัติ ไม่มีสิทธิ์ให้แสดงข้อความแทนเลขศูนย์ Sponsor ดูสรุปรวมเท่านั้น กราฟขั้นสูงและส่งออกรายงานยังพักอยู่

การเลือกบทบาทในเดโมหมายถึง **เปลี่ยนเป็นคนตัวอย่าง** ตามอาจารย์ จึงต้องบันทึก user_id ของคนนั้นและล้างข้อมูลหน้าก่อนหน้า ต่างจากฟังก์ชันใน SRS ที่คนเดียวถือหลายบทบาทแล้วสลับบทบาทใช้งาน บันทึกความต่างนี้ไว้สำหรับทบทวนภายหลัง

ถ้าเป็นระบบที่มี backend ให้ seed บัญชีแทนหน้าสมัคร และเก็บรหัสผ่านแบบ hash ฝั่ง server; ตัวเลือกคนเดโมเติมบัญชีเพื่อเข้าสู่ระบบผ่านการตรวจปกติ ไม่ใช่ส่ง role จาก browser แล้วให้ server เชื่อทันที

## 5. นำไฟล์เข้าระบบอย่างไร

### พฤติกรรมใน mockup ปัจจุบัน

DCC เลือก PDF ไม่เกิน 10 MB กรอกรหัส ชื่อ ประเภท Issue/Rev และวันที่มีผล พร้อมยืนยันว่าเป็นฉบับประกาศใช้เดิม ไฟล์เปิดผ่าน Blob URL ในหน้า ไม่มีการอัปโหลด server และรีโหลดแล้วข้อมูลหาย เจ้าของเอกสารเป็นบัญชีตัวอย่าง ส่วนงาน/ข้อมูลกำกับยังไม่ครบแบบฟอร์มระบบจริง

### เป้าหมายระบบจริง: นำเข้าเอกสารที่มีอยู่แล้ว

1. DCC เลือก PDF ทีละไฟล์ (เสนอเริ่ม PDF ก่อน; ชนิดไฟล์อื่นพักจากเดโม ไม่เปลี่ยน NFR ฉบับเต็ม)
2. กรอก/ตรวจรหัสเดิม ชื่อ ประเภท ส่วนงาน ฉบับ/Rev วันที่มีผล สถานะ และผู้รับผิดชอบจากหน้าปกจริง; อย่าอนุมานวันที่มีผลจากวันอัปโหลด
3. เก็บไฟล์บน server ในพื้นที่ไม่เปิดสาธารณะ และเก็บ metadata/ความสัมพันธ์ฉบับใน PostgreSQL ผ่าน Prisma ไม่เก็บแค่ชื่อไฟล์หรือ path จากเครื่องผู้ใช้
4. ใช้ storage key แยกจากชื่อไฟล์เดิม ตรวจชนิด/ขนาดตามข้อจำกัดที่ตกลง และตรวจสิทธิ์ทั้งอัปโหลด/ดาวน์โหลด
5. เพิ่มลงทะเบียนเมื่อบันทึกข้อมูลและไฟล์สำเร็จ ถ้าขั้นหนึ่งล้มเหลวต้องเก็บกวาดไฟล์ค้าง/ไม่แสดงรายการสำเร็จ
6. เปิดอ่าน/ดาวน์โหลดจากหน้ารายละเอียด รีโหลดและเริ่ม server ใหม่แล้วยังได้ไฟล์เดิม

**นำเข้าเดิม ≠ สร้างเอกสารใหม่:** การนำเข้าไม่ควรสร้าง DAR หรือประวัติอนุมัติย้อนหลังสมมติ และไม่เจนรหัสใหม่แทนรหัสต้นฉบับ การสร้างใหม่เข้ากระบวนการร่าง/DAR ตามสิทธิ์ ส่วนสถานะของเอกสารนำเข้าต้องอ้างหลักฐานเดิมและบันทึกผู้ทำการนำเข้า

หากต้องการให้ prototype เก็บข้อมูลข้ามการรีโหลด อาจเพิ่ม IndexedDB ภายหลัง แต่ **mockup ปัจจุบันยังไม่ได้ทำ** และการเก็บใน browser ไม่ทดแทนการทดสอบสิทธิ์ฝั่ง server

**ข้อมูลในหน้าทะเบียน:** รหัส ชื่อ ประเภท Rev/ฉบับ สถานะ วันที่มีผล ส่วนงาน ผู้รับผิดชอบ และการเปิดไฟล์; **รายละเอียด:** ข้อมูลดังกล่าว + ผู้จัดทำ/ทบทวน/อนุมัติที่มีหลักฐาน ประวัติฉบับ วันที่นำเข้า ผู้นำเข้า ชื่อ/ชนิด/ขนาดไฟล์ และ DAR อ้างอิงเมื่อมี ข้อมูลที่ไม่ทราบให้แสดงว่ายังไม่ระบุ

ตัวอย่างจริง `QP-2301-0107`: QP = ระเบียบปฏิบัติ, 2301 = หน่วยงานสำนักงานคณบดี, 01 = รหัสส่วนงาน, 07 = ลำดับระเบียบ; ต้นฉบับหน้าที่อ่าน **ยังไม่ให้ตารางแปลชื่อส่วนงานทั้งหมด** จึงห้ามเดาว่า 01 หมายถึงงานชื่อใด ต้องขอทะเบียนส่วนงาน/ทะเบียนเลขล่าสุดจาก DCC

ตัวอย่างจริง `FM-QP-2301-0107-01` = แบบฟอร์มลำดับ 01 ที่ผูกกับ QP-2301-0107 ไม่ใช่เลขแบบฟอร์มวิ่งรวมทุกหน่วยงาน

**ใน mockup:** ใช้ตัวนับในหน่วยความจำเริ่ม 90 ร่วมกันสำหรับตัวอย่าง QM/QP/WI เมื่อประกาศใช้ ไม่ใช่ทะเบียนเลขจริง; SD/FM ยังไม่ประกาศใช้ผ่าน DAR

**เป้าหมาย implementation ระบบจริง:** ผู้ใช้เลือกประเภท/ส่วนงาน/เอกสารแม่ตามกรณี ระบบแสดงรหัสตัวอย่าง และจองเลขจริงฝั่ง server ตอนสร้างสำเร็จด้วย transaction + unique constraint; ตั้งตัวนับจากทะเบียนเดิม ไม่ใช้จำนวนแถว+1 ไม่เริ่ม 01 ซ้ำ และไม่เปลี่ยน document_code เมื่อขึ้น Rev ใหม่ จุดจองเลขและการจัดการเลขที่ยกเลิกยังเป็นข้อตัดสินใจด้านออกแบบ ไม่ใช่ถ้อยคำที่ต้นฉบับสั่งไว้

ต้นฉบับมีลายน้ำ Uncontrolled Document จึงใช้ยืนยันรูปแบบที่อ่านพบและเตรียมข้อเสนอ ส่วนการใช้งานทางการยังต้องเทียบฉบับควบคุมตามรายการค้างเดิม; ข้อมูล SD แบบย่อใน mockup เก่าไม่ควรถูกใช้สร้างสูตรแทนหน้า 8

## 7. ลำดับพัฒนาระบบจริงและสิ่งที่พัก

| ระดับ | งาน |
|---|---|
| ต้องได้ก่อน | บัญชีเดโม/เลือกคน, ทะเบียนครบตามสิทธิ์, รายละเอียด/เปิด PDF, นำเข้าและเก็บไฟล์จริง, รหัสใหม่ไม่ซ้ำ, การตรวจสิทธิ์ระดับรายการ |
| เป้าหมายเส้นทางระบบจริง (ไม่ใช่สถานะว่า mockup ทำครบ) | QM/QP/WI/SD/FM ใหม่/แก้ไข → DAR ตรวจรับ → ทบทวน → อนุมัติ → ประกาศใช้ → บันทึกแจกจ่าย/เรียกคืนตามประเภท → ตรวจครบและปิด DAR (การรับทราบติดตามต่อฉบับตามข้อกำหนด); Finding → CAR → แผน → อนุมัติ → ผล/หลักฐาน → ตรวจ → ปิด; Dashboard 6 หมวดตามสิทธิ์ |
| พักจากรอบนี้ | สมัคร/ลืมรหัสผ่าน/จัดการบัญชีเต็มรูปแบบ, ยกเลิกใช้งานเอกสารใหม่, dashboard กราฟหลายแบบ, export หลายรูปแบบ, ค้นในเนื้อหา PDF/OCR, import จำนวนมาก, แจ้งเตือนภายนอก, แยกหน้าแต่ละขั้น, การตั้งค่าผ่าน UI ทุกชนิด |
| ห้ามตัดเพื่อให้เดโมง่าย | ตรวจครบและปิด DAR รวมหลักฐานแจกจ่าย/เรียกคืนที่จำเป็นตามประเภท, หลักแยกหน้าที่, การตรวจสิทธิ์ server ถ้ามี backend, ข้อห้ามข้ามขั้น CAR, แยกฉบับและไฟล์เดิม, ไม่สร้างเลขซ้ำ, เก็บ audit event พื้นฐาน, ไม่ประกาศสำเร็จเมื่อบันทึกล้มเหลว |

เก็บค่ากำหนดเวลารายขั้นเป็นข้อมูลตั้งค่า แม้พักหน้าตั้งค่าได้; คงการสำรอง DB และไฟล์แบบง่ายสำหรับการทดลอง/กู้คืน ไม่ถือว่าได้ทำระบบสำรองอัตโนมัติครบ NFR แล้ว

## 8. แผนพัฒนาระบบจริง 14 วันแบบมีจุดตัดสิน

ตารางนี้เป็นแผนเสนอ ไม่ใช่รายงานงานที่เสร็จใน mockup การปิด CAR ต้องได้ข้อยุติผู้ลงนามก่อนถือว่าทำวงจรครบ

สมมติผู้พัฒนา A/B ทำคู่กันและใช้ฐานข้อมูล/ตัวตนร่วมกัน หากมีผู้พัฒนาคนเดียวหรือ backend ยังไม่พร้อม ต้องลดเส้นทางก่อนรับปากวันส่ง

| วัน | ผลที่ควรเห็น |
|---|---|
| 1 | ตกลง 10 หน้า/เส้นทางเดโม, matrix, บัญชี, 14 บทบาท เส้นทาง QM/QP/WI และจุดอำนาจที่ค้าง |
| 2–3 | Login เดโม + ทะเบียน/รายละเอียด + อัปโหลด/เปิดไฟล์ + เจนรหัสและตรวจซ้ำ |
| 4–6 | A เดิน QM/QP/WI ผ่าน DAR และรับทราบ พร้อมบันทึกงานแจกจ่าย/เรียกคืนและตรวจครบก่อนปิด DAR; B เดิน Record/Audit/Finding/เปิดใบ ใช้ข้อมูลเอกสารร่วมกัน |
| 7–9 | แผน/อนุมัติ/ดำเนินการ/ตรวจ/ปิด CAR ด้วยคนต่างกัน เก็บ event และหลักฐาน |
| 10 | ค่าค้าง/เกินกำหนดและภาพรวมครบ 6 หมวดตามสิทธิ์ เชื่อมข้อมูลทั้งสองโมดูล |
| 11–12 | ทดสอบข้ามสิทธิ์ ส่งคำสั่งซ้ำ ไฟล์ผิด/หาย รีโหลดและกู้ข้อมูล ตรวจตัวเลข ทดสอบว่าปิด DAR ไม่ได้เมื่อหลักฐานขาดหรือไม่มีอำนาจ และปิดได้เมื่อครบพร้อมประวัติ |
| 13 | ซ้อมเดโม end-to-end และแก้จุดที่ทำเรื่องหลักไม่จบ |
| 14 | สำรองข้อมูล เตรียมชุดสาธิตและเวลาสำรอง ไม่เพิ่มฟีเจอร์ |

**จุดตัดสินวันที่ 3:** ถ้ายังอัปโหลด/เปิดไฟล์/บันทึกคงอยู่ไม่ได้ ให้หยุดเพิ่มหน้าและแก้แกนข้อมูลก่อน ลดกราฟ/รายงาน/การรองรับประเภทเอกสารเพิ่ม; ถ้าจะตัดวงจร A หรือ B ต้องแจ้งว่ายังไม่ครอบคลุมเป้าหมายโครงงาน ไม่แสดงว่าทำครบแล้ว

## 9. ประเด็นที่ยังต้องได้ข้อยุติก่อนส่งมอบระบบจริง

1. ส่งระบบที่บันทึกไฟล์จริงหรือ prototype ใน browser? ผู้พัฒนาจริงกี่คนและส่วนไหนพร้อมแล้ว?
2. ยืนยันขอบเขตระบบจริงจากแบบ 10 หน้า + 3 ป๊อปอัป และเส้นทาง QM/QP/WI/SD/FM ตามตาราง §6.2 ที่เลือกใช้ในระบบทดลอง; ยืนยันงานที่พักด้านรายงานและหน้าแยก โดยเก็บการปิด DAR และงานบังคับตามประเภทไว้
3. Mockup ใช้เลือกจาก 14 บัญชีแล้วเติม email/password ให้กดเข้าสู่ระบบ และสลับคนได้จากส่วนหัว; ต้องตกลงการเปิด/ปิดทางลัดนี้ในสภาพแวดล้อมระบบจริง
4. ขอทะเบียนเอกสาร/ส่วนงานและเลขล่าสุด เพื่อเจนรหัสไม่ชนของเดิม; เอกสารเดิมรักษารหัสไว้
5. ปิดข้อขัดแย้ง SRS: ผู้อนุมัติแผน CAR, จำนวนผู้ลงนามปิดใบ, ส่งกลับผลตรวจไม่ครบถ้วน, ผู้มีอำนาจมอบหมายรับทราบ และอำนาจ FM ที่ทะเบียนบทบาทกับตารางต้นฉบับหน้า 7 ไม่ตรงกัน

**ประโยคเสนออาจารย์:** “ขอทำ 10 หน้าหลัก ใช้บัญชีเดโมเลือกบทบาทแล้วเปลี่ยนคน เริ่มจากทะเบียนและไฟล์จริง ออกรหัสตามระเบียบ ใช้สิทธิ์แยกตามเมนู/งาน/ข้อมูล แสดง 14 บทบาท เส้นทาง QM/QP/WI และ Dashboard 6 หมวด โดย mockup ตอนนี้ปิด DAR ได้ ส่วน CAR ถึงรอปิดและยังต้องยืนยันผู้ลงนามก่อนทำวงจรให้จบในระบบจริง เก็บการตรวจครบและปิด DAR ในหน้าเดิม ส่วนจัดการผู้ใช้ รายงานขั้นสูง และหน้าแยกที่ไม่จำเป็นขอพักจากรอบสองสัปดาห์นี้ครับ”

## Step 3 — ข้อตกลง DAR สำหรับระบบจริง

- หนึ่ง DAR ต่อหนึ่งเอกสาร รองรับสร้างใหม่และแก้ไขทั้ง QM/QP/WI/SD/FM เท่านั้น ไม่เพิ่มคำขอยกเลิก/ถือครอง/อื่น ๆ ในรอบนี้
- ผู้คุมทะเบียน DAR ตรวจรับและปิดใบ; DCC ประกาศใช้ แยกจากการอนุมัติ
- อำนาจ QM: DCC → QMR → คณบดี; ประเภทอื่น: เจ้าของเอกสาร → รองคณบดี → QMR โดยมีตรวจรับก่อนทบทวน
- ยึด QP-2301-0107 §6.2 เป็นกฎระบบทดลองตามที่ผู้ใช้เลือก ข้อความอำนาจใน §4 ต่างกันบางจุดจึงไม่กล่าวว่าเป็นข้อยุติทางการของหน่วยงาน
- ส่งกลับต้องมีเหตุผลและตรวจรับรอบใหม่ ผลตรวจเก่าไม่รับรอง PDF ร่างใหม่; ไม่อนุมัติเป็นจุดจบของใบนั้น
- เลข DAR จองตอนส่งครั้งแรก ใช้ปีไทย เลขเดิมคงอยู่เมื่อส่งใหม่; CSV ปี 2568 มีถึง 068 จึงสงวนเลขถึง 068 โดยไม่สร้าง workflow ย้อนหลัง
- รหัสเอกสารใหม่จองตอนประกาศใช้ตามทะเบียนจริง; แก้ไขคงรหัสและเพิ่ม Revision โดยต้องทราบ Issue/Revision เดิมก่อน
- ผู้ช่วย QMR ทำแทนเฉพาะใบและขั้นที่มอบหมาย บันทึกผู้กระทำจริง; ผู้จัดทำห้ามอนุมัติของตนและผู้ทบทวนต้องต่างจากผู้อนุมัติ
- การแจกจ่าย/เรียกคืนบันทึกรายผู้ถือครอง วันที่ และหลักฐาน หรือเหตุผลว่าไม่เกี่ยวข้องก่อนปิดใบ ไม่ตีความเป็นการรับทราบเนื้อหา หน้ารับทราบทำในขั้นถัดไป
- เอกสารนำเข้าเดิมที่ไม่มีเจ้าของให้ DCC ระบุจากผู้รับผิดชอบจริงก่อนเปิด DAR แก้ไข ไม่สมมติให้ทุกบัญชีเป็นเจ้าของ
- ไม่แก้ข้อมูลฉบับประกาศใช้จากร่าง และไม่ประกาศทับกรณีฉบับต้นทางเปลี่ยนระหว่างพิจารณา
