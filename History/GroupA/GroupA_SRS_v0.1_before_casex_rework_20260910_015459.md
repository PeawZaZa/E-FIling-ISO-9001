# 1. Introduction

## 1.1 Purpose

เอกสารนี้กำหนดความต้องการซอฟต์แวร์ของโมดูลควบคุมเอกสารคุณภาพ การจัดการคำขอดำเนินการเอกสาร (Document Action Request: DAR) การเผยแพร่ และการรับทราบเอกสาร ภายในระบบ E-Filing ของสำนักงานคณบดีคณะวิศวกรรมศาสตร์ มหาวิทยาลัยเทคโนโลยีราชมงคลล้านนา

เอกสารจัดทำขึ้นเพื่อให้ผู้จัดทำโครงงาน อาจารย์ที่ปรึกษา ผู้ใช้งาน ผู้พัฒนา และผู้ทดสอบ ใช้ตรวจสอบขอบเขต หน้าที่ของระบบ สิทธิ์การดำเนินการ กฎทางธุรกิจ และเกณฑ์การยอมรับร่วมกัน ก่อนนำไปออกแบบ พัฒนา และทดสอบ โดยข้อกำหนดต้องสามารถสอบกลับไปยังเอกสารโครงงาน ระเบียบปฏิบัติ แบบฟอร์ม หรือข้อตัดสินใจที่เกี่ยวข้องได้

ขอบเขตของเอกสารฉบับนี้จำกัดเฉพาะส่วนความรับผิดชอบของกลุ่ม A ซึ่งทำงานร่วมกับโมดูลของกลุ่ม B ภายในระบบเดียวกัน โดยใช้ข้อมูลและกติกาส่วนร่วมอย่างสอดคล้องกัน เอกสารฉบับนี้จะใช้ประกอบการจัดทำ SRS รวมของระบบในภายหลัง

เอกสารอยู่ในสถานะร่างเพื่อทบทวน (Working Draft) โดยจัดทำและตรวจสอบทีละหัวข้อ ประเด็นที่เอกสารต้นทางขัดแย้งกันหรือยังไม่ได้ข้อสรุปจะระบุเป็นรายการรอยืนยัน และไม่ถือเป็นข้อกำหนดที่ได้รับอนุมัติ

## 1.2 Document Conventions

### 1.2.1 รหัสที่ใช้ในเอกสาร

| รหัส | ความหมาย |
| :--- | :--- |
| `FR-A-xx` | ความต้องการเชิงหน้าที่ (Functional Requirement) ของโมดูล A |
| `NFR-A-xx` | ความต้องการนอกเหนือหน้าที่ (Nonfunctional Requirement) |
| `BR-A-xx` | กฎทางธุรกิจ (Business Rule) ที่ระบบต้องบังคับใช้ |
| `CON-A-xx` | ข้อจำกัด (Constraint) ที่กำหนดจากภายนอก |
| `US-A-xx` | เรื่องเล่าของผู้ใช้ (User Story) |
| `UC-A-xx` | กรณีการใช้งาน (Use Case) |
| `AC-A-xx` | เกณฑ์การยอมรับ (Acceptance Criterion) แบบ Given–When–Then |
| `M-A-xx` | องค์ประกอบของแบบจำลอง (Model Element) ในภาคผนวก B |
| `TBD-A-xx` | ประเด็นรอยืนยัน พร้อมผู้รับผิดชอบและหลักฐานที่ใช้ปิดประเด็น |
| `REF-A-xx` | เอกสารต้นทางที่เปิดตรวจสอบแล้ว โดยระบุเวอร์ชันและส่วนที่นำมาใช้ใน §1.5 |
| `OBJ-A-1.2.x` | วัตถุประสงค์ของโครงงานตามหัวข้อ 1.2.x ในบทที่ 1 ของกลุ่ม A |

ใช้ส่วนรหัส `-A-` เพื่อแยกข้อกำหนด แหล่งอ้างอิง และวัตถุประสงค์จากโมดูล B เมื่อจัดทำเอกสารรวม รหัสเดิมที่นำมาอ้างต้องระบุชื่อเอกสารและเวอร์ชันประกอบ และจัดทำตารางเทียบกับรหัสใหม่เพื่อรักษาการสอบกลับ ไม่ถือว่ารหัสที่เหมือนกันในเอกสารต่างฉบับมีความหมายเดียวกัน

### 1.2.2 ระดับความจำเป็นของข้อความ

| คำที่ใช้ | ความหมาย |
| :--- | :--- |
| **ต้อง** (Must / shall) | ข้อกำหนดที่จำเป็นและทวนสอบได้ คำว่า **ห้าม** ใช้ระบุพฤติกรรมที่ต้องไม่เกิดขึ้น |
| **ควร** (Should) | ข้อกำหนดลำดับรอง โดยระบุเงื่อนไขหรือเหตุผลประกอบให้ตรวจสอบได้ |
| **Provisional** | ข้อเสนอหรือค่าตั้งต้นที่ยังไม่ผ่านการยืนยัน ห้ามถือเป็นกฎที่อนุมัติแล้ว และต้องเชื่อมกับ `TBD-A-xx` |
| **⚠️** | จุดที่ต้องตรวจสอบหรือมีข้อขัดแย้ง รวมถึงค่าที่ทีมเสนอขึ้นเอง ต้องมีรายการ `TBD-A-xx` คู่กันในภาคผนวก C |

ระดับความจำเป็นกับสถานะการยืนยันเป็นคนละเรื่อง ข้อความที่ใช้คำว่า “ต้อง” อาจยังเป็น Provisional ได้ และยังไม่ถือเป็นข้อกำหนดที่อนุมัติจนกว่าจะปิดประเด็นที่เกี่ยวข้อง การใช้เครื่องหมายรอยืนยันไม่ใช่เหตุให้สร้างตัวเลขกำหนดเวลาหรือเกณฑ์ทดสอบที่ไม่มีหลักฐาน

### 1.2.3 ศัพท์ที่ต้องไม่ใช้ปะปนกัน

| ศัพท์ | ความแตกต่างที่ใช้ในเอกสาร |
| :--- | :--- |
| **เอกสาร (Document)** / **บันทึก (Record)** | เอกสารใช้กำหนดหรือสนับสนุนการปฏิบัติงาน ส่วนบันทึกเป็นหลักฐานของผลหรือกิจกรรมที่ดำเนินการแล้ว แบบฟอร์มเปล่ากับบันทึกที่กรอกแล้วจึงต้องแยกความหมาย |
| **ฉบับที่ (Issue)** / **แก้ไขครั้งที่ (Revision)** | เป็นข้อมูลแยกช่องตาม Master List ไม่รวมเป็นค่าเวอร์ชันเดียว กฎการเพิ่มค่าต้องพิจารณาจากหลักฐานและระบุในข้อกำหนดที่เกี่ยวข้อง |
| **ทบทวน (Review)** / **อนุมัติ (Approve)** | การตรวจความถูกต้องและความครบถ้วน กับการตัดสินใจอนุญาตให้ดำเนินการ เป็นคนละการกระทำ ผู้มีอำนาจและลำดับจะกำหนดในรายละเอียดที่ผ่านการทบทวน |
| **ถือครอง/รับสำเนา** / **รับทราบเนื้อหา (Acknowledgement)** | การมีหรือรับสำเนาเอกสารไม่ยืนยันโดยอัตโนมัติว่าบุคคลนั้นรับทราบเนื้อหา ต้องแยกเหตุการณ์และหลักฐานที่ใช้ยืนยัน |
| **ฉบับปัจจุบัน** / **สำเนาควบคุม (Controlled Copy)** | ฉบับปัจจุบันบอกว่าเอกสารฉบับใดมีผลใช้งาน ส่วนสำเนาควบคุมบอกลักษณะการควบคุมสำเนา ไฟล์ของฉบับปัจจุบันไม่ถือเป็นสำเนาควบคุมโดยอัตโนมัติ |
| **อนุมัติ DAR** / **ปิด DAR** | การอนุมัติคำขอไม่เท่ากับดำเนินงานครบจนปิดคำขอ เงื่อนไขปิดต้องพิจารณาตามประเภทคำขอและงานที่เกี่ยวข้อง โดยไม่บังคับทุกคำขอให้ทำขั้นตอนเหมือนกัน |

ใช้ชื่อ **ใบขอดำเนินการเอกสาร (Document Action Request: DAR)** ตามแบบฟอร์มจริง รายละเอียดศัพท์จะอ้างอิงจากอภิธานศัพท์ในภาคผนวก A ส่วนตารางนี้ใช้ป้องกันการตีความปะปน ไม่ได้กำหนดสิทธิ์หรืออนุมัติกระบวนการเพิ่มเติม

### 1.2.4 ภาษาที่ใช้ตั้งชื่อสถานะและบทบาท

| สิ่งที่ตั้งชื่อ | ภาษาที่ใช้ | ใช้ที่ไหน |
| :--- | :--- | :--- |
| **ชื่อสถานะและชื่อบทบาท** | ภาษาไทยเป็นชื่อหลัก | เอกสาร ส่วนติดต่อผู้ใช้ ข้อความแจ้งเตือน และรายงานที่ส่งออก |
| **รหัสสถานะและรหัสบทบาท** | รหัสภาษาอังกฤษ ตัวพิมพ์ใหญ่คั่นด้วยขีดล่าง | ฐานข้อมูล ส่วนเชื่อมต่อภายในระบบ และโค้ดโปรแกรม |

ห้ามนำรหัสสถานะและรหัสบทบาทภาษาอังกฤษไปแสดงแทนชื่อภาษาไทยต่อผู้ใช้ ให้จัดทำตารางจับคู่ชื่อกับรหัสเป็นแหล่งอ้างอิงเดียวสำหรับแต่ละชุดข้อมูล และให้หัวข้ออื่นอ้างถึงตารางดังกล่าวแทนการทำสำเนา โดยจะกำหนดตำแหน่งตารางเมื่อร่างรายละเอียดส่วนที่เกี่ยวข้อง

ชื่อสถานะที่เสนอเพื่อใช้ในซอฟต์แวร์ต้องระบุว่าเป็นการออกแบบพฤติกรรมของระบบ ไม่กล่าวว่าเป็นชื่อที่ QP กำหนดโดยตรงหากต้นฉบับไม่ได้ระบุ และไม่แปลงทุกกิจกรรมหรือช่องในแบบฟอร์มเป็นสถานะโดยอัตโนมัติ

ผู้อ่านควรตรวจสถานะเอกสารและรายการรอยืนยันก่อนนำข้อกำหนดไปใช้ กลุ่มผู้อ่านในหัวข้อนี้ไม่ใช่การกำหนดบทบาทหรือสิทธิ์ในซอฟต์แวร์

## 1.4 Product Scope

### 1.4.1 เป้าหมายของผลิตภัณฑ์

โมดูลควบคุมเอกสารเป็นส่วนหนึ่งของระบบ E-Filing สำหรับสำนักงานคณบดีคณะวิศวกรรมศาสตร์ มีเป้าหมายให้ผู้เกี่ยวข้องเข้าถึงเอกสารที่ถูกต้อง ติดตามการดำเนินการคำขอ ตรวจสอบประวัติการเปลี่ยนแปลง และสอบกลับหลักฐานการรับทราบเอกสารได้

โมดูลนี้รับผิดชอบข้อมูลหลักและฉบับของเอกสาร ส่วนโมดูลอื่นอ้างอิงข้อมูลดังกล่าวภายในระบบเดียวกัน การมีฉบับใหม่ไม่ควรทำให้รายการที่อ้างอิงฉบับเดิมสูญเสียความหมายในการสอบกลับ

### 1.4.2 ขอบเขตที่รองรับ

| งาน | ขอบเขต |
| :--- | :--- |
| ทะเบียนเอกสาร | จัดการรหัส ชื่อ ประเภท เจ้าของเอกสาร ฉบับที่ แก้ไขครั้งที่ วันที่มีผลใช้ และข้อมูลประกอบ |
| ไฟล์เอกสาร | อัปโหลดและเข้าถึงไฟล์ที่สัมพันธ์กับฉบับเอกสารตามสิทธิ์ |
| คำขอดำเนินการเอกสาร | จัดทำ ส่ง และติดตามคำขอ DAR พร้อมรายละเอียดและเอกสารแนบ โดยประเภทคำขอที่รองรับต้องผ่านการยืนยัน (`TBD-A-01`) |
| การพิจารณา | บันทึกการตรวจความครบถ้วน การทบทวน และการอนุมัติ/ไม่อนุมัติ ตามอำนาจที่ได้รับการยืนยัน (`TBD-A-02`) |
| การประกาศใช้และควบคุมฉบับ | ประกาศใช้เอกสารที่ผ่านการอนุมัติ ควบคุมฉบับปัจจุบัน และแยกฉบับยกเลิกออกจากการใช้งานทั่วไป |
| การรับทราบ | กำหนดผู้รับทราบและบันทึกการยืนยันรับทราบโดยผูกกับบุคคล เวลา และฉบับเอกสาร |
| การค้นหาและติดตาม | ค้นหาเอกสาร ตรวจประวัติการแก้ไข และติดตามคำขอหรืองานที่เกี่ยวข้องตามสิทธิ์ |
| การสอบกลับ | บันทึกผู้ดำเนินการ การกระทำ เวลา และข้อมูลประกอบเหตุการณ์สำคัญ |
| ข้อมูลร่วม | ให้ส่วนที่เกี่ยวข้องของระบบอ้างอิงข้อมูลเอกสาร ฉบับ สถานะ และการรับทราบตามสิทธิ์ |

การมีรายการในตารางนี้ไม่ได้ยืนยันรายละเอียดทุกขั้นตอน สิทธิ์ และข้อยกเว้นจะกำหนดใน §4 และกฎทางธุรกิจ

- การจัดทำเนื้อหาเอกสารแทนเจ้าของงาน การตัดสินความถูกต้องเชิงวิชาชีพ และการอนุมัติแทนผู้มีอำนาจ

- ระบบบริหารความเสี่ยงและระบบบริหารการประชุมทบทวนฝ่ายบริหาร
- การกำหนดหรือแก้ความต้องการ Records, Audit/Finding, CAR และ Dashboard ที่อยู่ในเอกสาร B

ข้อความในเอกสาร A เดิมที่กล่าวถึง Dashboard ขั้นสูงไม่ถือเป็นการเพิ่มขอบเขตให้ B

# 2. Overall Description

## 2.1 Product Perspective

โมดูล A ทำงานบนระบบ E-Filing เดียวกันกับโมดูล B โดยใช้บัญชีผู้ใช้ บทบาท และข้อมูลหน่วยงานร่วมกัน ข้อมูลหลักและฉบับเอกสารอยู่ภายใต้ความรับผิดชอบของโมดูลควบคุมเอกสาร ไม่สร้างทะเบียนเอกสารซ้ำเพื่อรองรับแต่ละโมดูล

ระบบใช้สถาปัตยกรรมสามชั้นร่วมกับการออกแบบบริการแบบแยกส่วน ได้แก่ ส่วนติดต่อผู้ใช้ ส่วนประมวลผล และส่วนข้อมูล ขอบเขตระหว่างโมดูลใช้จัดความรับผิดชอบภายในระบบ ไม่ใช่การแยกระบบใช้งานออกจากกัน

## 2.2 Product Functions

ความสามารถหลักประกอบด้วย:

1. จัดการทะเบียนและไฟล์ของฉบับเอกสาร
2. จัดทำและติดตามคำขอ DAR
3. สนับสนุนการตรวจ ทบทวน และพิจารณาคำขอตามอำนาจ
4. ควบคุมการประกาศใช้และการยกเลิกฉบับเอกสาร
5. กำหนดและติดตามการรับทราบเอกสาร
6. ค้นหาเอกสารและตรวจประวัติการดำเนินการ
7. ให้ข้อมูลเอกสารและการรับทราบแก่ส่วนที่เกี่ยวข้องภายในระบบตามสิทธิ์

การถือครอง แจกจ่าย เรียกคืน ทำลาย ทบทวนตามรอบ และส่งออกรายงาน ยังมีสถานะตาม §1.4.3 ไม่ถือว่าได้รับอนุมัติจากการกล่าวถึงในภาพรวม

## 2.3 User Classes and Characteristics

| กลุ่มผู้ใช้งานตามหน้าที่ | ลักษณะการใช้งาน |
| :--- | :--- |
| เจ้าของงาน/ผู้จัดทำเอกสาร | เตรียมเอกสารและรายละเอียดคำขอ ติดตามผล และแก้ไขตามความเห็น |
| เจ้าหน้าที่ควบคุมเอกสาร | ตรวจความครบถ้วน ควบคุมทะเบียน และดำเนินการเกี่ยวกับฉบับเอกสารตามอำนาจ |
| ผู้ทบทวน | ตรวจความถูกต้องและความเหมาะสมของเอกสารในขอบเขตที่รับผิดชอบ |
| ผู้อนุมัติ | พิจารณาเอกสารหรือคำขอภายใต้อำนาจที่กำหนด |
| ผู้ใช้งานเอกสาร | ค้นหา เข้าถึง และยืนยันรับทราบเอกสารที่เกี่ยวข้อง |
| ผู้ดูแลระบบร่วม | ดูแลบัญชีและการมอบหมายบทบาทตามกติกาส่วนกลาง การเป็นผู้ดูแลระบบไม่ให้สิทธิ์อนุมัติเอกสารโดยอัตโนมัติ |

ตารางนี้เป็นการจำแนกหน้าที่ ยังไม่ล็อกจำนวนบทบาทระบบหรือจับคู่ตำแหน่งทุกตำแหน่งเข้ากับบทบาท (`TBD-A-06`)

ผู้ใช้หนึ่งคนอาจได้รับหลายบทบาท แต่ใช้งานครั้งละหนึ่งบทบาท การอนุญาตให้ดำเนินการต้องพิจารณาบทบาทที่กำลังใช้งานร่วมกับขอบเขตข้อมูลและหน้าที่ที่ได้รับมอบหมาย การเปลี่ยนบทบาทไม่เพิ่มอำนาจที่บุคคลนั้นไม่ได้รับมอบหมาย

## 2.4 Operating Environment

ระบบเป็นเว็บแอปพลิเคชันที่ปรับการแสดงผลให้เหมาะกับคอมพิวเตอร์และอุปกรณ์เคลื่อนที่ ใช้งานผ่านเบราว์เซอร์และเครือข่ายที่เชื่อมต่อถึงเครื่องแม่ข่าย

ชุดเทคโนโลยีที่กำหนดในโครงการคือ React, Node.js/Express, PostgreSQL และ Prisma ส่วนรุ่นซอฟต์แวร์ เบราว์เซอร์ที่รองรับ และทรัพยากรเครื่องแม่ข่ายต้องยืนยันจากสภาพแวดล้อมติดตั้งจริง ไม่กำหนดจากข้อมูลเครื่องพัฒนาคนใดคนหนึ่ง (`TBD-A-07`)

## 2.5 Design and Implementation Constraints

- ใช้ข้อมูลผู้ใช้ บทบาท หน่วยงาน และเอกสารชุดร่วมตามขอบเขตความรับผิดชอบ
- รักษาความหมายของข้อมูลต้นฉบับ เช่น Issue และ Revision และการอ้างอิงฉบับเอกสาร
- ใช้ภาษาไทยสำหรับชื่อสถานะและบทบาทที่ผู้ใช้เห็นตาม §1.2
- การเปลี่ยนวิธีปฏิบัติจากกระดาษเป็นดิจิทัลต้องไม่ถูกตีความว่าเปลี่ยนอำนาจอนุมัติหรือสถานะสำเนาโดยอัตโนมัติ (`TBD-A-02`, `TBD-A-04`)
- ไม่เพิ่มการเชื่อมต่อภายนอกหรือฟังก์ชันนอกขอบเขตจากเพียงการมีเอกสารรองรับ
- ค่าจำกัดและกฎที่ยังไม่มีข้อสรุปต้องเชื่อมกับรายการรอยืนยัน

## 2.6 User Documentation

เสนอให้จัดทำคู่มือสำหรับงานหลัก ได้แก่ การค้นหาและรับทราบเอกสาร การจัดทำและติดตาม DAR การทบทวน/พิจารณา และการควบคุมทะเบียน

คู่มือต้องใช้ชื่อสถานะและคำเรียกเดียวกับระบบ อธิบายเงื่อนไขก่อนดำเนินการ ความหมายของผลลัพธ์ และวิธีแก้ไขเมื่อข้อมูลไม่ผ่านการตรวจ โดยจัดทำฉบับใช้งานหลังขั้นตอนและสิทธิ์ได้รับการยืนยันแล้ว

## 2.7 Assumptions and Dependencies

- หน่วยงานจะยืนยันผู้มีอำนาจและการมอบหมายหน้าที่ตามประเภทเอกสาร (`TBD-A-02`, `TBD-A-06`)
- มีบัญชีผู้ใช้ บทบาท และข้อมูลหน่วยงานร่วมที่ตรวจสอบตัวตนของผู้ดำเนินการได้
- เอกสารตั้งต้นที่จะนำเข้าระบบต้องได้รับการตรวจรหัส ฉบับ และสถานะก่อนใช้จริง
- การรับรองผลดำเนินงานทางกายภาพ เช่น คืนหรือทำลายกระดาษ อาศัยการบันทึกจากผู้รับผิดชอบ
- ข้อตกลงข้อมูลภายในระบบต้องได้รับการตรวจร่วมก่อนพัฒนา (`TBD-A-08`)
- ไฟล์ QP ที่ตรวจมีลายน้ำ Uncontrolled Document จึงยังต้องยืนยันฉบับที่ใช้อ้างอิงเป็นข้อผูกพันกับหน่วยงาน (`TBD-A-10`)

| มุมมอง | ข้อมูลและการกระทำหลัก |
| :--- | :--- |
| เข้าสู่ระบบและเลือกบทบาท | แสดงบทบาทที่ผู้ใช้ได้รับและบทบาทที่กำลังใช้งาน พร้อมการสลับบทบาท |
| ค้นหาเอกสาร | ค้นหาด้วยรหัส ชื่อ ประเภท และสถานะ ภายในสิทธิ์ โดยเน้นฉบับปัจจุบันสำหรับการใช้งานทั่วไป |
| รายละเอียดเอกสาร | แสดงข้อมูลหลัก Issue, Revision วันที่มีผลใช้ สถานะ และไฟล์ที่เข้าถึงได้ |
| จัดทำคำขอ DAR | แสดงข้อมูลที่ต้องกรอกตามประเภทคำขอ เอกสารที่เกี่ยวข้อง และข้อผิดพลาดที่ต้องแก้ |
| ติดตามคำขอ | แสดงความคืบหน้า ประวัติการดำเนินการ ความเห็น และงานที่ผู้ใช้ต้องทำต่อ |
| งานรอตรวจ/พิจารณา | แสดงรายการที่ผู้ใช้มีอำนาจดำเนินการ พร้อมข้อมูลและไฟล์ฉบับที่นำมาพิจารณา |
| ควบคุมทะเบียนและประกาศใช้ | แสดงข้อมูลและการกระทำที่ได้รับอนุญาตเกี่ยวกับการขึ้นทะเบียน ประกาศใช้ และยกเลิก |
| รับทราบเอกสาร | แสดงฉบับที่ต้องรับทราบและผลการยืนยันของผู้ใช้ |
| ประวัติการดำเนินการ | แสดงผู้ดำเนินการ การกระทำ เวลา และข้อมูลประกอบตามสิทธิ์ |

**กติกาการตอบสนอง**

- แสดงชื่อสถานะภาษาไทยและแยกสถานะเอกสารออกจากสถานะ DAR
- เมื่อข้อมูลไม่ครบ ให้ระบุช่องและเหตุผลที่ต้องแก้
- เมื่อดำเนินการไม่สำเร็จ ต้องไม่แสดงว่าเสร็จสมบูรณ์
- การเปิดหน้าจอหรือเห็นปุ่มไม่ถือเป็นสิทธิ์ดำเนินการ ระบบต้องตรวจสิทธิ์เมื่อรับคำสั่งด้วย
- มุมมองของงานที่ยังรอยืนยันใน §1.4.3 จะเพิ่มหลังตัดสินขอบเขตแล้ว

## 3.2 Hardware Interfaces

ระบบไม่กำหนดส่วนเชื่อมต่อฮาร์ดแวร์เฉพาะ ผู้ใช้เข้าถึงผ่านอุปกรณ์ที่เปิดเว็บเบราว์เซอร์ได้และมีการเชื่อมต่อเครือข่าย

การเลือกไฟล์จากอุปกรณ์ผู้ใช้ไม่ถือเป็นการเชื่อมต่อเครื่องสแกน ส่วนพื้นที่จัดเก็บไฟล์และอุปกรณ์สำรองข้อมูลเป็นองค์ประกอบของสภาพแวดล้อมติดตั้ง ซึ่งต้องกำหนดรายละเอียดร่วมกับผู้รับผิดชอบระบบ

## 3.3 Software Interfaces

### 3.3.1 ข้อมูลร่วมภายในระบบ

| ชุดข้อมูล | การใช้ |
| :--- | :--- |
| ผู้ใช้ บทบาท และหน่วยงาน | ระบุตัวผู้ดำเนินการ บทบาทใช้งาน และขอบเขตข้อมูล |
| ข้อมูลหลักเอกสาร | อ้างอิงตัวเอกสารโดยไม่สร้างทะเบียนซ้ำ |
| ฉบับเอกสาร | อ้างอิงฉบับเฉพาะ พร้อม Issue, Revision สถานะ และวันที่มีผลใช้ |
| ไฟล์เอกสาร | เข้าถึงไฟล์ที่สัมพันธ์กับฉบับและผ่านการตรวจสิทธิ์ |
| การรับทราบ | อ้างอิงผลการรับทราบที่ผูกกับผู้ใช้และฉบับเอกสาร |

รหัสที่ต้องพิจารณาให้สอดคล้องกับข้อตกลงที่ระบุใน B ได้แก่ `user_id`, `role_id`, `department_id`, `document_id`, `document_code`, `version_id` และ `file_id` โดยยังไม่ล็อกชนิดข้อมูลหรือรูปแบบ API (`TBD-A-08`)

`version_id` ใช้ระบุฉบับอ้างอิงภายในระบบ ไม่ใช้แทนความหมายของ Issue และ Revision (`TBD-A-05`)

### 3.3.2 พฤติกรรมเมื่อข้อมูลไม่พร้อม

หากไม่สามารถตรวจสิทธิ์หรืออ่านข้อมูลที่จำเป็นต่อการดำเนินการได้ ระบบต้องไม่รายงานว่าดำเนินการสำเร็จ หากส่วนสรุปอ่านข้อมูลไม่ได้ ต้องแสดงว่าไม่พร้อมใช้งาน ไม่แสดงเป็นศูนย์หรือไม่มีรายการจนทำให้เข้าใจผิด

### 3.3.3 ขอบเขตการเชื่อมต่อ

การเชื่อมต่อฐานข้อมูล พื้นที่เก็บไฟล์ และบริการยืนยันตัวตนร่วมเป็นส่วนภายในระบบ การเชื่อมต่อ LDAP/Active Directory, HR และการส่งอีเมลยังอยู่นอกขอบเขตฉบับนี้

## 3.4 Communications Interfaces

การสื่อสารระหว่างเบราว์เซอร์กับระบบที่ใช้งานจริงผ่าน HTTPS และมีการตรวจตัวตนและสิทธิ์ก่อนอ่านข้อมูลหรือรับคำสั่ง

การส่งไฟล์ต้องรายงานผลสำเร็จหรือข้อผิดพลาดอย่างชัดเจน โดยชนิดไฟล์ ขนาดสูงสุด ระยะเวลารอ และวิธีจัดการการส่งซ้ำจะกำหนดในข้อกำหนดที่เกี่ยวข้องหลังมีข้อมูลรองรับ (`TBD-A-09`)

ระบบไม่รับประกันการใช้งานแบบออฟไลน์ในขอบเขตร่างนี้ และไม่กำหนดให้การสื่อสารระหว่างโมดูลต้องเป็นการเรียกผ่านเครือข่าย เนื่องจากเป็นส่วนประกอบภายในระบบเดียวกัน
