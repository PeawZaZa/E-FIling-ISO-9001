## 2. ก่อนเริ่มสาธิตสด

1. เริ่ม PostgreSQL ที่เตรียมไว้หากยังไม่ทำงาน แล้วรัน `npm run dev` จากโฟลเดอร์ `efiling/` ห้ามรัน `db:seed`, reset, restore หรือ deploy migration ระหว่างเตรียมเดโม เพราะ schema ปัจจุบันเป็นเวอร์ชันล่าสุดแล้ว
2. ตรวจว่า `http://127.0.0.1:3001/api/health` และ `/api/health/db` ตอบกลับ `{"status":"ok"}` จากนั้นเปิด `http://127.0.0.1:5173`
3. `.env` ของเครื่องปัจจุบันมี `DATABASE_URL` และ `API_PORT` แล้ว เมื่อไม่มีตัวแปร override ระบบจะใช้ `.local/document-storage` และ `.local/record-storage` เป็นที่จัดเก็บเอกสารและ Records
4. เตรียมไฟล์ขนาดเล็กและไม่มีข้อมูลลับเพียง 2 ไฟล์ ได้แก่ PDF ที่เปิดได้จริงสำหรับเอกสารเดโมใหม่ และ PDF หรือ JPEG ที่เปิดได้จริงสำหรับหลักฐาน ใช้ run ID ที่ไม่ซ้ำ เช่น `FINAL-DEMO-25690922-A` ในชื่อข้อมูลใหม่ทุกจุด
5. บันทึกค่า baseline ของ Dashboard ก่อนเปลี่ยนข้อมูล ฐานปัจจุบันไม่มี workflow record ที่นำกลับมาใช้ซ้ำได้ การเดโมแบบเปลี่ยนสถานะครบเส้นทางจึงต้องสร้าง chain ที่ควบคุมได้หนึ่งชุดผ่าน UI ห้ามกล่าวอ้างว่ามีข้อมูลดังกล่าวอยู่แล้ว

บัญชีเดโมทุกบัญชีใช้รหัสผ่าน `Demo1234!`

### จังหวะการสาธิตสดที่แนะนำ

- ช่วงเปิดแบบอ่านอย่างเดียว: ขั้น 1–3
- Workflow หลักที่ควบคุมได้: ขั้น 4–8 โดยใช้ run ID และ Record หลักฐานอย่างละหนึ่งชุด
- มุมมองผู้บริหารและสรุปเรื่องสิทธิ์: ขั้น 9
- หากเวลาจำกัด ให้เตรียม record ผ่าน UI ไว้ที่สถานะยืนยันก่อนหน้าคำสั่งที่จะสาธิต จด ID ของรายการ และห้ามซ้อมคำสั่งเปลี่ยนสถานะสุดท้ายกับ record ชุดเดียวกัน

## 4. การสลับบทบาทและจุดสาธิตเรื่องสิทธิ์

ไม่ต้องสาธิตสิทธิ์ทุกคู่ในตาราง ให้ใช้จุดต่อไปนี้เพื่อแสดงขอบเขตการควบคุมโดยไม่สร้างข้อมูลเพิ่ม:

| บทบาท | จุดสาธิตที่เป็นประโยชน์ |
|---|---|
| DCC | เห็นทะเบียนเอกสารทั้งหมด จัดการการประกาศใช้/รับทราบ จัดการงานตรวจ และ Dashboard ปฏิบัติการ ห้ามนำเสนอว่า DCC มีอำนาจปิด CAR/NCR |
| QMR | ทบทวน DAR ประเภท QM อนุมัติ DAR ที่ไม่ใช่ QM และอนุมัติแผน CAR/NCR เฉพาะเมื่อไม่ได้เป็นผู้จัดทำแผน |
| Lead Auditor | สร้างรอบตรวจ/Finding และแสดงการเข้าถึงตามขอบเขต การเป็น Lead เพียงอย่างเดียวไม่ได้ให้อำนาจปิดใบหรือเป็นผู้ตรวจแทนในเรื่องที่ยังไม่ยืนยัน |
| Auditor | บันทึก Finding และตรวจประสิทธิผลเมื่อเป็นผู้แจ้งเดิมและไม่ใช่ผู้รับผิดชอบใบ |
| ผู้รับผิดชอบ/ผู้ปฏิบัติงานทั่วไป | ใช้ Car Owner แสดงการแก้ไข สาเหตุ/แผน ผลและหลักฐาน; ใช้ Reader แสดงการอ่านเอกสารทั่วไปและการรับทราบของตนเอง ทั้งสองบทบาทอนุมัติขั้นที่ระบบแยกหน้าที่ให้ตนเองไม่ได้ |
| Sponsor | แสดงเฉพาะยอดรวมใน Dashboard ต้องไม่มีเมนูธุรกรรม รายละเอียดรายการ หรือ drill-down |

ใช้ตัวสลับบัญชีเดโมในระบบเพื่อประหยัดเวลา แต่ต้องทดสอบ logout/login จริงอย่างน้อยหนึ่งครั้งใน smoke check หลังสลับบัญชีให้ใช้ Back/Forward หนึ่งครั้งเพื่อแสดงว่าคำสั่งหรือข้อมูลจากบทบาทก่อนหน้าไม่ค้างอยู่

## 5. ขอบเขตกฎธุรกิจ CAR/NCR

เส้นทางที่ยืนยันสำหรับการสาธิตสิ้นสุดที่ `PENDING_CLOSURE`

- ผู้ตรวจประสิทธิผลคือ Auditor/Lead Auditor เดิมที่แจ้ง Finding และต้องไม่ใช่ผู้รับผิดชอบใบ
- ห้ามลองหรือสื่อว่ามีการปิดใบหลัง `PENDING_CLOSURE` เพราะผู้มีอำนาจปิดใบยังเป็น TBD
- หาก DCC เป็นผู้แจ้ง Finding ผู้ตรวจประสิทธิผลที่มีอำนาจยังเป็น TBD ใบนั้นต้องคงสถานะถูกพักพร้อมข้อความอธิบาย ห้ามอนุมานให้ DCC, QMR หรือ Lead Auditor มีอำนาจแทน

รายการเหล่านี้เป็นขอบเขตกฎธุรกิจที่ทราบอยู่แล้ว ไม่ใช่ความล้มเหลวของการเดโม

## 6. ความปลอดภัยระหว่างการสาธิต

- ห้าม seed, reset, restore, ลบ, แก้ PostgreSQL โดยตรง หรือแทนที่ไฟล์ใน storage ทั้งสองแห่ง
- ถือว่าเอกสารควบคุมปัจจุบัน 295 รายการและไฟล์ 296 ไฟล์เป็นข้อมูลอ่านอย่างเดียว โดยเฉพาะห้ามใช้เอกสารกลางทำ DAR แก้ไขฉบับระหว่างเดโม เพราะข้อมูลนำเข้าหลายรายการยังไม่มีหลักฐานยืนยัน Issue/Revision/เจ้าของครบ
- DAR ที่เปลี่ยนสถานะต้องใช้เอกสาร run ID ใหม่ เมื่อเปลี่ยนสถานะแล้วจะย้อนกลับเพื่อซ้อมใหม่ไม่ได้ ให้เก็บ record เป็นประวัติและเปลี่ยน suffix หากจำเป็นต้องรันรอบใหม่
- ห้ามยืนยันการรับทราบระหว่างซ้อม หากต้องสงวนการเปลี่ยนจากรอรับทราบเป็นรับทราบแล้วไว้สาธิตสด
- ห้ามเปิด CAR/NCR ใบที่สองจาก Finding เดิม การป้องกันใบซ้ำเป็นพฤติกรรมที่ตั้งใจไว้
- ห้ามใช้ Finding ที่ DCC เป็นผู้แจ้งสำหรับเส้นทาง CAR/NCR หลัก ห้ามอนุมัติแผนของตนเอง และห้ามพยายามปิดใบหลัง `PENDING_CLOSURE`
- ใช้หลักฐาน PDF/JPEG ขนาดเล็กที่ไม่มีข้อมูลลับ ห้ามใช้ไฟล์ที่เปลี่ยนนามสกุลให้ดูเหมือน PDF หรือไฟล์ ISO ต้นทางขนาดใหญ่ในการสาธิต upload
- หากพบข้อผิดพลาดที่ไม่คาดคิด ให้หยุดการเปลี่ยนสถานะของ record นั้น บันทึกบัญชี เวลา หน้า/hash และข้อความ จากนั้นใช้ run ID ใหม่เฉพาะเมื่อเข้าใจปัญหาแล้วและจำเป็นต้องมี record ใหม่จริง ๆ

## 7. UI smoke checklist แบบย่อ

บันทึกผลเป็น `PASS`, `FAIL`, `BLOCKED` หรือ `N/A` checklist นี้ไม่ใช้แทน `docs/MANUAL_UI_ACCEPTANCE.md`

- [ ] Login ด้วย DCC, refresh, logout แล้ว login ใหม่ และตรวจว่ารหัสผ่านผิดแสดงข้อความที่เข้าใจได้
- [ ] สลับ DCC → Sponsor → Reader ตรวจว่า sidebar/navigation เปลี่ยน และ hash ของหน้าที่ไม่มีสิทธิ์ไม่ทำให้ข้อมูลรั่ว
- [ ] ค้นหารายการเอกสาร เปิดรายละเอียด เปิด PDF และดาวน์โหลดไฟล์
- [ ] ทำ DAR transition ที่ปลอดภัยหนึ่งขั้นกับ record ของ run ID และตรวจสถานะ/ประวัติบนหน้าจอ
- [ ] มอบหมายและยืนยันการรับทราบหนึ่งรายการของเอกสาร run ID หรืออ่านผลที่ยืนยันแล้วโดยไม่เปลี่ยนข้อมูล
- [ ] สร้าง/เปิด Record ของ run ID แล้ว upload/download หลักฐานอย่างปลอดภัย
- [ ] เปิด Audit → Finding → CAR/NCR และตรวจว่าลิงก์นำกลับไปยัง record ที่ถูกต้อง
- [ ] เปิด Dashboard ด้วย DCC และ Sponsor ทดลอง drill-down ที่ DCC มีสิทธิ์หนึ่งรายการ และยืนยันว่า Sponsor ไม่มี drill-down
- [ ] สังเกต loading state ที่เกิดขึ้นตามธรรมชาติและตัวกรองที่ได้ผลลัพธ์ศูนย์ ทดสอบ connection error เฉพาะเมื่อผู้ควบคุมเดโมอนุญาตให้หยุด API โดยชัดเจน และห้ามหยุด PostgreSQL ใน smoke pass นี้

## 8. ขอบเขตและข้อจำกัดที่ตรวจสอบแล้ว

### ฟังก์ชัน MVP ที่ยืนยันแล้ว

- Login/session สำหรับเดโม และสิทธิ์ระดับโมดูล/API ตามบทบาทของบัญชีคงที่ 14 บัญชี
- รายการ/รายละเอียด/PDF ของเอกสารควบคุม, เส้นทาง DAR สำหรับ QM/QP/WI/SD/FM, การรับทราบแยกตามฉบับ, Records/Evidence, Audit/Finding, CAR/NCR ถึง `PENDING_CLOSURE` และ Dashboard 6 หมวดที่จำกัดข้อมูลตามบทบาท
- การเชื่อมต่อฐานข้อมูลปัจจุบัน migration ที่ใช้แล้ว ความพร้อมของไฟล์อ้างอิง และ checksum ของเอกสารควบคุม

### ฟังก์ชันที่เลื่อนไปหลัง MVP

- ระบบยืนยันตัวตน/session สำหรับ production และการ deploy หลาย process; เดโมปัจจุบันใช้บัญชีคงที่และ session store ในหน่วยความจำ
- กราฟ Dashboard ขั้นสูงและการ export
- การทดสอบ load/soak และการรับรองทุกอุปกรณ์/browser/accessibility อย่างครบถ้วน

### กฎธุรกิจที่ยังเป็น TBD

- ผู้มีอำนาจปิด CAR/NCR หลัง `PENDING_CLOSURE` และการส่งกลับจากขั้นปิดใบ
- ผู้ตรวจประสิทธิผลเมื่อ DCC เป็นผู้แจ้ง Finding
- การมอบหมายผู้ตรวจ/ผู้ช่วยรายใบ แหล่ง Finding เพิ่มเติม/การจัดการ Observation และกำหนดเวลารายขั้นอัตโนมัติในส่วนที่นโยบายยังไม่ยืนยัน
- นโยบายรายชื่อผู้รับทราบสำหรับ production; การให้ DCC เลือกเป็นกฎของระบบเดโมที่ยืนยันแล้วเท่านั้น

### การตรวจโครงสร้างพื้นฐานที่ยังค้าง

- ยังไม่ได้รันหรือลงนามรับรอง UI smoke checklist แบบย่อข้างต้นและ manual UI acceptance checklist ฉบับเต็ม
- รอบตรวจความพร้อมนี้ยังไม่ได้ restart PostgreSQL/ระบบปฏิบัติการจริงและทดสอบการกู้ session ใน browser; เมื่อ restart API session ในหน่วยความจำจะหายและต้อง login ใหม่
- เตรียมเครื่องมือ backup/restore แล้ว แต่ยังไม่ได้ทดสอบ restore ลงฐานข้อมูลและ storage ว่างบนเครื่องหรือ environment แยกจริง
