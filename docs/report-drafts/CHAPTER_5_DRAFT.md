# บทที่ 5

# สรุปผลและข้อเสนอแนะ

บทนี้สรุปผลโครงงาน E-Filing ISO 9001 เทียบกับวัตถุประสงค์ที่ระบุไว้ในร่างบทที่ 1 โดยอาศัยผลการพัฒนาและการตรวจสอบในบทที่ 4 ข้อสรุปจำกัดอยู่ที่ระบบทดลองขั้นต่ำ (MVP) และผลตรวจที่บันทึกไว้ถึงวันที่ 22 กันยายน 2569 จึงไม่ใช้แทนผลตรวจรับผ่านหน้าจอทั้งหมดหรือผลการนำระบบไปใช้งานจริง

## 5.1 สรุปผลการดำเนินงาน

### 5.1.1 ระบบที่พัฒนาได้

โครงงานพัฒนาเว็บแอปพลิเคชัน E-Filing เป็นระบบเดียวที่ใช้บัญชี สิทธิ์ และข้อมูลร่วมกันระหว่างทะเบียนเอกสารควบคุม การดำเนิน DAR การรับทราบเอกสาร บันทึกและหลักฐานดิจิทัล การตรวจติดตามและประเด็นที่พบ CAR/NCR และ Dashboard ผู้มีสิทธิ์สามารถดำเนินงานตามบทบาทและอ้างอิงข้อมูลข้ามส่วนงานได้โดยไม่แยกเป็นระบบเอกสารกับระบบติดตามคุณภาพคนละชุด

ผลตรวจระดับระบบ/API แสดงเส้นทางเชื่อมจาก DAR และเอกสารฉบับที่ประกาศใช้ ไปสู่การรับทราบ Record และ Evidence, Finding, CAR และข้อมูลสรุปใน Dashboard รวมถึงการปฏิเสธการกระทำที่ผิดสิทธิ์หรือผิดลำดับงานตามกรณีที่ทดสอบ การรับทราบผูกกับผู้รับและฉบับเอกสาร ส่วน Dashboard จำกัดข้อมูลตามสิทธิ์ก่อนคำนวณยอดรวม ผลดังกล่าวแสดงความสามารถในการเชื่อมข้อมูลและสอบกลับภายในขอบเขตทดสอบ แต่ไม่ใช่หลักฐานว่ากระบวนการทำงานจริงมีระยะเวลาสั้นลง ลดข้อผิดพลาด หรือได้รับความพึงพอใจจากผู้ใช้แล้ว

### 5.1.2 ผลตามวัตถุประสงค์ของโครงงาน

วัตถุประสงค์เจ็ดข้อในหัวข้อ 1.2 ยังเป็นถ้อยคำร่างสำหรับรายงานฉบับรวม ตารางที่ 5.1 จึงประเมินผลตามร่างดังกล่าวโดยใช้หลักฐานในบทที่ 4 และแยกส่วนที่ทำงานได้ในระบบทดลองออกจากส่วนที่ยังไม่ครบหรือยังไม่ได้ตรวจรับผ่านหน้าจอ การสรุปผลรายข้อสำหรับรายงานฉบับส่งต้องทวนกับวัตถุประสงค์ฉบับที่อาจารย์ที่ปรึกษาอนุมัติอีกครั้ง

**ตารางที่ 5.1** สรุปผลตามวัตถุประสงค์ในร่างบทที่ 1

| วัตถุประสงค์ | ผลที่มีหลักฐานรองรับ | ข้อสรุปในขอบเขตโครงงาน |
|---|---|---|
| ข้อ 1 ทะเบียนและฉบับเอกสาร | มีทะเบียน รายละเอียด ฉบับ และไฟล์ PDF ที่ผู้มีสิทธิ์เข้าถึงได้; ชุดเอกสารปัจจุบันผ่านการตรวจไฟล์ตามที่รายงานในบทที่ 4 | มีผลรองรับบางส่วน; ยังต้องยืนยันผลการค้นหาตามวัตถุประสงค์และตรวจรับ UI ครบชุด |
| ข้อ 2 DAR และการรับทราบ | เส้นทาง DAR ที่รองรับผ่านการทดสอบตั้งแต่ยื่นคำขอถึงประกาศใช้และตรวจเงื่อนไขก่อนปิด; ผลรับทราบผูกกับผู้ใช้และฉบับเอกสาร | พัฒนาและตรวจได้ในขอบเขต MVP; กติกาอำนาจสำหรับใช้งานจริงบางส่วนยังต้องยืนยัน |
| ข้อ 3 ทะเบียน Record และ Evidence | สร้าง แก้ไข ค้นหา ดูและดาวน์โหลดหลักฐานได้ตามสิทธิ์ พร้อมอ้างอิงเอกสารและใช้หลักฐานในงานที่เกี่ยวข้อง | พัฒนาและตรวจได้ในขอบเขต MVP |
| ข้อ 4 รอบตรวจและ Finding | บันทึกรอบตรวจ ทีม เกณฑ์/ขอบเขต และ Finding พร้อมหลักฐานอ้างอิง โดยตรวจสิทธิ์และเงื่อนไขความเป็นอิสระ | พัฒนาและตรวจได้ในขอบเขต MVP ไม่ใช่ระบบบริหารกระบวนการตรวจติดตามทุกขั้นของหน่วยงาน |
| ข้อ 5 การติดตาม CAR/NCR จนถึงปิดใบ | การเปิดใบ การแก้ไข การจัดทำและอนุมัติแผนโดย QMR การบันทึกผล และการตรวจประสิทธิผลมีผลทดสอบ; สถานะสุดท้ายคือ `PENDING_CLOSURE` | บรรลุบางส่วน; ยังไม่ดำเนินการปิดใบขั้นสุดท้าย เพราะอำนาจและกติกาขั้นปิดยังไม่ยืนยัน |
| ข้อ 6 ติดตามสถานะ กำหนดเวลา และ Dashboard | Dashboard สรุปข้อมูลหกหมวดตามสิทธิ์และเชื่อมรายการงานที่รองรับ; กำหนดเวลารายขั้นแบบอัตโนมัติยังไม่เป็นข้อยุติ | บรรลุบางส่วน; การสรุปและติดตามสถานะอยู่ใน MVP แต่กติกากำหนดเวลาอัตโนมัติยังไม่ครบ |
| ข้อ 7 ความเชื่อมโยงและประวัติการดำเนินงาน | การทดสอบเส้นทางข้ามโมดูลตรวจข้อมูลอ้างอิง ประวัติเหตุการณ์ และข้อมูลสรุปที่สัมพันธ์กับรายการต้นทาง | พัฒนาและตรวจได้ในเส้นทาง API ที่ทดสอบ; ยังต้องตรวจรับการใช้งานจริงผ่านหน้าจอ |

[ข้อมูลที่ต้องยืนยันจากผู้จัดทำ: จำนวนข้อและถ้อยคำวัตถุประสงค์ฉบับรวมที่อาจารย์ที่ปรึกษาอนุมัติ ก่อนสรุปผลการบรรลุรายข้อในรายงานฉบับส่ง]

### 5.1.3 ความหมายและขอบเขตของผลตรวจ

ผล System/API E2E ที่บันทึกไว้ผ่าน 11/11 รายการทดสอบระดับบน และมีการตรวจ NCR เฉพาะเส้นทางเพิ่มเติมถึงสถานะ `PENDING_CLOSURE` ผลเหล่านี้สนับสนุนข้อสรุปว่ากฎสิทธิ์ ความสัมพันธ์ของข้อมูล และเส้นทางหลักที่ทดสอบทำงานร่วมกันได้ในสภาพแวดล้อมทดสอบ อย่างไรก็ดี รายการทดสอบอัตโนมัติไม่ครอบคลุมปฏิสัมพันธ์ทั้งหมดของผู้ใช้บนเบราว์เซอร์ ภาระงานระยะยาว หรือความพร้อมสำหรับเปิดใช้จริง ผลประโยชน์ที่กล่าวไว้ในบทที่ 1 จึงยังเป็นประโยชน์ที่คาดหวัง ไม่ใช่ผลลัพธ์เชิงปริมาณที่พิสูจน์แล้ว

## 5.2 ข้อจำกัดและประเด็นที่ยังไม่เสร็จสมบูรณ์

### 5.2.1 ข้อจำกัดด้านลำดับงานและกฎทางธุรกิจ

การตรวจประสิทธิผลของ CAR/NCR เป็นคนละขั้นกับการอนุมัติแผนและการปิดใบ QMR อนุมัติแผนตามกติกาของระบบทดลอง แต่ไม่ใช่ผู้ปิดใบโดยอัตโนมัติ ผลการพัฒนาปัจจุบันหยุดที่ `PENDING_CLOSURE` เพราะผู้มีอำนาจลงนามปิดและการส่งกลับจากขั้นปิดยังไม่มีข้อยุติ กรณี DCC เป็นผู้แจ้ง Finding ก็ยังไม่มีผู้ตรวจประสิทธิผลแทนที่ได้รับการยืนยัน จึงไม่ควรเพิ่มสิทธิ์ให้บทบาทอื่นจากการคาดเดา

กติกาอื่นที่ต้องยืนยันก่อนขยายการใช้งาน ได้แก่ อำนาจและรายชื่อผู้รับทราบสำหรับงานจริง การมอบหมายผู้ตรวจหรือผู้ช่วยรายใบ แหล่ง Finding และประเภทประเด็นที่จะเปิด CAR/NCR ได้ ตลอดจนค่ากำหนดเวลารายขั้นอัตโนมัติ ข้อความอำนาจบางส่วนของระเบียบ DAR ยังไม่ตรงกัน แม้ระบบทดลองเลือกแนวทางที่ได้รับมติสำหรับการสาธิตแล้ว การเลือกดังกล่าวไม่ถือเป็นการยุติข้อขัดแย้งเชิงนโยบายของหน่วยงาน

### 5.2.2 ข้อจำกัดด้านการตรวจรับและการนำไปใช้จริง

การตรวจผ่าน API และการเตรียมรายการทดสอบผ่านเบราว์เซอร์ยังไม่เท่ากับการตรวจรับ UI ที่เสร็จสิ้น ยังไม่มีบันทึกผลรับรองการทดสอบผ่านหน้าจอเต็มชุด และฐานข้อมูลปัจจุบันยังไม่มีข้อมูลธุรกรรมของเส้นทางสาธิตต่อเนื่องที่สร้างผ่าน UI จึงไม่สรุปว่าผู้ใช้ได้ตรวจรับทุกขั้นหรือเห็นผลในหน้าจอจริงครบแล้ว

ด้านการสำรองและกู้คืนมีขั้นตอนและเครื่องมือช่วยพร้อมผลตรวจเงื่อนไขป้องกัน แต่ยังไม่ได้สร้างชุดสำรองจริงและกู้คืนลงฐานข้อมูลกับพื้นที่ไฟล์ว่างในสภาพแวดล้อมแยก ความพร้อมด้านการจัดการตัวตน/เซสชันและการติดตั้งใช้งาน production ก็อยู่นอกผลยืนยันของระบบสาธิตรอบนี้ จึงยังไม่อาจสรุปว่าระบบพร้อมใช้งานจริงหรือพร้อมกู้คืนจากเหตุขัดข้อง

## 5.3 ข้อเสนอแนะ

### 5.3.1 งานที่ควรดำเนินการก่อนพิจารณาใช้งานจริง

ควรให้ผู้มีอำนาจของหน่วยงานยืนยันและบันทึกมติเรื่องการปิด CAR/NCR ผู้ตรวจประสิทธิผลในกรณี DCC แจ้ง Finding และกติกาสิทธิ์ที่ยังค้าง ก่อนพัฒนาคำสั่งหรือเปิดใช้งานขั้นตอนดังกล่าว จากนั้นตรวจความสอดคล้องของลำดับ DAR และขอบเขตผู้รับทราบกับระเบียบที่อนุมัติใช้จริง เพื่อไม่ให้กติกาของระบบทดลองถูกตีความเป็นนโยบายถาวร

ควรดำเนินการตรวจรับผ่านเบราว์เซอร์ด้วยชุดกรณีที่เตรียมไว้ บันทึกผู้ทดสอบ สภาพแวดล้อม ผล PASS/FAIL และข้อบกพร่องตามจริง พร้อมเก็บภาพหน้าจอจากระบบปัจจุบันสำหรับบทผลการดำเนินงาน ควรทดสอบการสร้างชุดสำรองและกู้คืนในฐานข้อมูลและพื้นที่ไฟล์ว่างที่แยกจากระบบเดิม แล้วตรวจข้อมูลอ้างอิง ไฟล์ สิทธิ์ และประวัติหลังการกู้คืนตามรายการตรวจ ก่อนอ้างความพร้อมด้านการกู้คืน

### 5.3.2 แนวทางพัฒนาต่อหลังยืนยันงานหลัก

เมื่อกติกาธุรกิจและผลตรวจรับหลักได้รับการยืนยันแล้ว จึงควรพิจารณาการจัดการตัวตนและเซสชันสำหรับสภาพแวดล้อมใช้งานจริง รวมถึงการทดสอบภาระงานและการปฏิบัติการที่สอดคล้องกับสภาพแวดล้อมเป้าหมาย การปรับส่วนติดต่อผู้ใช้ควรอาศัยข้อสังเกตจากการตรวจรับและผู้ใช้จริง ไม่สรุปความสะดวกหรือความพึงพอใจล่วงหน้า ส่วนรายงานส่งออก การวิเคราะห์ขั้นสูง หรือการแจ้งเตือนเพิ่มเติมควรจัดลำดับภายหลังตามความต้องการที่ยืนยันแล้ว ไม่ใช่ถือว่าเป็นผลที่โครงงานรอบปัจจุบันพัฒนาเสร็จ

โดยสรุป ระบบทดลองแสดงความเป็นไปได้ของการเชื่อมงานเอกสารและการติดตามคุณภาพในแอปพลิเคชันเดียวตามเส้นทางที่ทดสอบ แต่การสรุปว่าบรรลุวัตถุประสงค์ฉบับอนุมัติครบทุกข้อ และการนำระบบไปใช้จริง ยังขึ้นกับข้อยุติด้านอำนาจ ผลตรวจรับผ่านหน้าจอ และผลทดสอบการกู้คืนที่ยังต้องดำเนินการ
